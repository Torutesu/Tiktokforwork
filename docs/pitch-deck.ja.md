## 0. タイトル

**TikTok for Work**
承認したら、もう動いている。

- サブ: チームの判断を、縦フィードで一枚ずつ。スワイプで決めて、AI が実行する。
- 下部にロゴ 2 つ相当のワードマーク: **Daytona**（一判断一サンドボックス）／**Neo4j**（判断グラフ）

## 1. 問題（承認は二度、チームの時間を奪う）

小さなチーム（3〜10 人で複数事業・複数リポジトリ）の一日を具体的に:

**承認の前:**「ホテルの予約サイト、税込表示にして」と言われた承認者は、
1. GitHub を開いて「どこを触るのか」「壊れないか」を見る
2. Slack を遡って「前に似た話をどう決めたか」を探す
3. 「今ゆいが触ってる決済ページとぶつからないか」を本人に聞く
→ 判断そのものより、**判断の材料集め**に時間が消える。

**承認の後:**「OK」と言っても、誰かがコードを書き、テストを回し、PR を出すまで止まる。
→ 小さなチームでは「承認済み・未着手」が平均 2 日転がる。

**既存ツールの限界:** Slack の承認はただの「いいね」。GitHub の PR は作られてからしか見えない。
どちらも「判断する瞬間」に証拠がなく、「判断した瞬間」に何も起きない。

- 画面: なし（数字を大きく: 「3 つのツール」「2 日」）

## 2. プロダクト（TikTok のように、判断が一枚ずつ流れてくる）

- 人は**自分の AI とだけ**話す。チャンネルも DM も受信箱もない。
- AI が組織の役割・権限を見て、決めるべき人に **Decision Card** として届ける。
- カードは縦フィードに一枚ずつ。**右スワイプで承認、左で却下。**
- 決まったことは GitHub に同期され、事業ごとに自動で分類される。

「TikTok を見るのと同じ指の動きで、会社の判断が片づく」

- 画面: `02-card-arrives.png`（届いた直後のカード。タイトル・要約・事業ラベル・依頼者）

---

## 3. 今回の革新（カードが「証拠」を持ってくる）

**あなたが開く前に、あなたの AI が済ませておく:**

1. **やってみた** — Daytona のサンドボックスでリポジトリを開き、変更を当て、テストを走らせ、プレビューを立てる
2. **思い出した** — Neo4j の判断グラフに「前にこの事業でどう決めたか」「誰の作業とぶつかるか」を聞く
3. **見せる** — 結果がカードに浮かび上がる（14 tests passed / 2 files / 前回は 12 日前にあなたが承認 / ゆいの作業と競合）

そして**右スワイプした瞬間に、テスト済みのブランチが push され、PR が開く。**

- 画面: `03-evidence-running.png` → `04-evidence-done.png`（作業中 → 完了の 2 枚を並べる）
- 一言: 「判断に、証拠と実行を同梱した」

## 5. Daytona の使い方（各 AI が自分のクラウドコンピュータを持つ）

**設計:** Grok の各ボットが自分のマシンを持つように、**メンバーごとの AI に 1 台の「デスク」**（永続サンドボックス）。
そこにリポジトリと依存が入っていて、**判断が届くたびにデスクを fork** して子サンドボックスを作る。

| Daytona の機能 | この製品での役割 | 画面で見える形 |
|---|---|---|
| 永続サンドボックス（`desk-<user>`、自動停止なし） | AI の常駐マシン。エージェント本体もここで動く（`deploy-desk`） | 艦隊画面の「DESK desk-tanaka · started」 |
| **fork**（ミリ秒で複製、checkout と node_modules 込み） | 一判断一サンドボックス。clone も install もしないので dry-run は「編集＋テスト」だけ | 「Forked my desk into a fresh sandbox · 184 ms」 |
| `process.executeCommand` / `fs.uploadFile` | LLM の編集を当てて `npm test` | 「Applied 2 edits」「14 passed, 0 failed」 |
| **preview link**（ポート公開） | 変更後のサイトをカードから開ける | 「▶ Open the preview」ボタン |
| ラベル + list | 誰の AI がどのマシンで何を検証中か | 艦隊画面（3 agents / 5 sandboxes / 2 checking） |
| 承認まで生かしておき、承認で push、却下で delete | テストしたブランチをそのまま出す。使い捨て | 「Pushed the tested branch」→「PR #12 is open」 |

**なぜ Daytona でないと成立しないか:** カードは並列に、いつでも生まれる。CI のキューやラップトップでは「見る前に証拠がある」にならない。**サブ秒起動・fork・使い捨て・プレビュー**の 4 つが揃って初めて「届いた時にはもう試してある」が UX になる。

- 画面: `04b-fleet.png`（チームの AI 一覧。デスクとサンドボックスが見える）

## 6. Neo4j の使い方（判断が次の判断の文脈になる）

**グラフ:** Person / Business / Decision / Repo / PR をノードに、
REQUESTED / ASSIGNED_TO / DECIDED_BY / ABOUT / TOUCHES / PRODUCED をエッジに。

カードが届くたびに 2 本の Cypher:
- **前例:** 同じ事業の過去の決定を新しい順に（誰が・いつ・承認か却下か）
- **競合:** 同じリポジトリに触れている open なカードと、その担当者

結果は 1 文に要約されてカードに載る:
「Hotel Sakura に関する直近 3 件のうち 2 件をあなたが承認。最新は 12 日前。ゆいの open カードが同じリポジトリに触れている」

**なぜグラフか:** 「この事業の直近の承認者 → その PR → 触ったファイル → 今それを触っている人」は 3〜4 ホップの問い。行テーブルでは書けず、グラフなら 1 クエリ・ミリ秒。判断・PR は起きた瞬間に書き戻され、**2 枚目のカードは 1 枚目の承認を前例として知っている**（デモの最後）。

- 画面: `07-second-evidence.png`（2 枚目のカード。「You approved a pricing change on this site just now」）+ Neo4j Browser のグラフ画面（当日撮影）

## 7. 仕組み（変えていないもの、足したもの）

```
フィード（Web / iOS） ⇄ リレー（Cloudflare Workers・Durable Objects・D1） ⇄ GitHub
                                   ⇅ 同じ AG-UI プロトコル
                        agent/（受信者の AI）— Daytona デスク上で稼働
                                   ├─ Daytona: fork → edit → test → preview → push
                                   └─ Neo4j: 前例・競合 → 要約 → 記録
```

- リレーとクライアントは**無変更**。リレーは「カードを更新できるのは受信者本人だけ」というルールを持つ。エージェントは受信者のセッションで参加するので、その人のカードだけを豊かにできる（他人のカードには触れない）。
- 証拠は `card.evidence` として構造化され、UI がそれを描く。UI を持たない古いクライアントにも `context` の文字列として届く。

---

## 8. 「TikTok くらい簡単」であることの証明

- 操作は**変わらない**。届く → 読む → スワイプ。増えた操作はゼロ。
- 増えたのは**情報**（証拠）と**結果**（PR）だけ。
- 判断にかかる時間の比較（当日、2 人に同じカードを見せて計る）: 証拠なし vs 証拠あり。
- 「承認＝実行」を怖がる人がいるか（いれば push を承認後に保つ今の設計が正しい）。

## 9. 現状と次

**動いている:** フィード・ルーティング・リアルタイム同期・GitHub 同期・事業分類／エージェント（デスク・fork・テスト・プレビュー・push・PR）／Neo4j 同期と 2 本のクエリ／艦隊画面／デモモード（`?demo`）。

**次:**
- 影響範囲: 1 つの承認が変える他の open な判断
- 複数案の並列 fork（同じ依頼を 3 通り試して、テストが通った案だけ見せる）
- コード以外の dry-run（価格表・契約・スケジュール）
- グラフによるルーティング（前例が「誰が決めるべきか」を決める）
