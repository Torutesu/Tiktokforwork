How it works

The recipient's AI, made real

1 · REQUEST

Toru tells their AI

"Show tax-inclusive prices on the hotel booking site."

2 · ROUTE

Relay picks the approver

Org graph, roles and approval authority decide it goes to Tanaka.

3 · EVIDENCE

Tanaka's AI does the homework

Neo4j: precedent and collisions.
Daytona: clone, edit, test.
Both land on the card in place.

4 · DECIDE

Tanaka swipes right

One look at the evidence, one decision.

5 · EXECUTE

Branch pushed, PR opened

From the same sandbox. Decision and PR recorded in the graph. Result card back to Toru.

The agent is a separate process that joins the relay as the recipient over the same AG-UI protocol the feed clients use. The relay lets only a card's recipient update it, which is exactly what lets the agent enrich that person's cards and nobody else's. No change to the relay or the clients.

TikTok for Work05
Daytona

One sandbox per decision

StepIn the sandbox
1daytona.create(), sub-second, fully isolated
2git clone, git checkout -b agent/card-…
3The model proposes edits; applied with fs.uploadFile
4npm test → pass / fail counts, diff stats
5Approve → git push + PR from this sandbox.
Anything else → sandbox.delete()

Why Daytona and not a CI job or a laptop

  • Cards are created continuously and in parallel. A queue would put the evidence after the decision.
  • Sub-second, disposable environments make "the evidence is there before you look" possible.
  • The sandbox outlives the dry-run: the approval pushes the exact branch that was tested.
  • A failed run is still evidence. The card says so; the approver decides with it.

Neo4j

Decisions become context for the next decision

(:Person)-[:REQUESTED]->(:Decision)
(:Decision)-[:ASSIGNED_TO]->(:Person)
(:Decision)-[:DECIDED_BY {action, at}]->(:Person)
(:Decision)-[:ABOUT]->(:Business)
(:Decision)-[:TOUCHES]->(:Repo)
(:Decision)-[:PRODUCED]->(:PR)

// Precedent: what did we decide about this business?
MATCH (d:Decision {id:$id})-[:ABOUT]->(b)<-[:ABOUT]-(p)
WHERE p.action IS NOT NULL
OPTIONAL MATCH (p)-[r:DECIDED_BY]->(who)
RETURN p.title, p.action, r.at, who.login
ORDER BY r.at DESC LIMIT 5

// Collision: who is working on this code right now?
MATCH (d {id:$id})-[:TOUCHES]->(r)<-[:TOUCHES]-(o)
      -[:ASSIGNED_TO]->(p)
WHERE o.action IS NULL
RETURN o.title, p.login

Why a graph

  • "Who approved the last three decisions about this business, what PRs came out of them, and who is touching that code now" is a multi-hop question.
  • Rows can't answer it; the graph answers it in one query, per card, in milliseconds.
  • Seeded from the relay's state snapshot on join. Every decision and every PR is written back as it happens.
  • The rows become one sentence on the card, in the reader's language, and stay on it as data.
